# Medusa v2 BAS price synchronization

Use this when changing `bas-prices.ts` or the product sync price path. Verify exact workflow signatures against the installed `node_modules/@medusajs/core-flows/dist` declarations and implementation before modifying them.

1. Convert BAS minor units to Medusa major units precisely. No sale: base price = BAS `price`; with `original_price > price`: base = `original_price`, BAS-owned `sale` price = `price`. Never write a zero BAS price: quarantine the product without overwriting its old price.
2. Create product/variant first, resolve its Medusa IDs, then sync prices. For an existing variant, call `upsertVariantPricesWorkflow(container).run({ input: { variantPrices: [{ product_id, variant_id, prices: [{ id: existingBasePriceId, amount, currency_code }] }], previousVariantIds: [variant_id] } })`; omit the price ID only when creating a missing base row. In the inspected Medusa v2 implementation, a variant omitted from `previousVariantIds` is treated as NEW and gets a second price set. Including its ID in both arrays updates the linked set without unlinking it (`arrayDifference`).
3. Query variant's price set and base row, but do NOT infer BAS sale ownership from `product_variant.price_set.prices` alone: the observed graph returned only the base row even when sale rows existed. Fetch the singleton price list marked `metadata.bas_price_sync === true` with its prices, match sale rows by `price_set_id` AND `currency_code`, and reject duplicate owned lists or multiple matching rows. Do not match a list by title, and never alter an unmarked/manual list.
4. Create a missing list only once, as `type: 'sale'`, `status: 'active'`, marker metadata and `prices: []`; add/update/remove rows via `batchPriceListPricesWorkflow`. When BAS stops supplying `original_price`, set base to current and delete only that variant/currency's BAS-owned sale row. Avoid price writes on identical repeat syncs. If paginating lists/prices, fetch all pages before concluding no match; a truncated result can silently create duplicates.
5. Test pure planning with RED→GREEN, then run on a fresh DB clone: create → identical repeat → changed base/sale → removed sale. Query actual `price`, `price_set`, `product_variant_price_set`, and `price_list` rows, including row IDs and ownership marker. Require exactly one linked base and at most one BAS sale row per variant/currency after every pass; inspect calculated storefront prices. A passing process or unit suite alone is not evidence of idempotence.
